# 개발용 평가

32개 문제는 새로 구성한 개발용 사례이며 GOLD가 아니에요. 원문의 예시를 변형한 것은 lineage_group으로 묶었어요. 모두 개발용으로 공개되어 있어 블라인드 테스트라고 부르지 않아요.

`inputs.jsonl`은 작성 모델에 제공할 입력만 담아요. `rubrics.jsonl`은 결과를 받은 뒤 평가자에게 제공해요. 두 파일과 예상 해법은 실행 스킬/ChatGPT 지식 파일에 포함하지 않아요.

자동 스키마 검사는 문구 품질 평가가 아니에요. 현재 Codex·Claude Code·새 ChatGPT 세션에서의 모델 실행 기록은 없어요. 모델이 실행되면 모델 이름·버전·환경·스킬 버전·전체 응답·평가자·날짜를 기록해야 해요.

## 실행 절차

1. 동일 버전 패키지를 각 환경에 설치하거나 프로젝트에 설정해요.
2. 새 세션에서 inputs의 과제 하나와 조건을 전달해요. 명시 호출·암시 호출을 구분해서 기록해요.
3. 응답을 그대로 저장해요. 성공 사례만 골라 기록하지 않아요.
4. rubrics와 실제 입력을 함께 보고 검토해요. 표현 일치가 아니라 허용 해법·중요 정보·개입 범위·변수 보존을 확인해요.
5. 오류 유형과 심각도를 기록하고 사용자 검토로 평가자의 오판도 확인해요.

권장 보고 항목: 중요 사실 오류, 중요 결과 누락, 불필요한 수정, 정보 손실을 낳는 삭제, 문구만으로 UI 문제를 덮은 사례, 선호 수용 여부. 점수는 시험 범위와 표본 수를 함께 표시해요.

개발용 문제가 안정되면 회귀 검증에 사용할 수 있어요. 최종 검증용 문제는 나중에 별도 확보하고, 규칙을 고치면서 본 정답을 계속 블라인드라고 부르지 않아요.

## v0.1.1 이후 생성 관계

문제 정의는 `development-cases.jsonl` 한 곳에서 바꿔요. 빌드하면 `inputs.jsonl`과 `rubrics.jsonl`이 정확한 필드 투영으로 다시 생성돼요. 입력 원문을 canonical JSON으로 정규화한 SHA256을 두 파일에 같이 기록해요. 직접 바꾼 파생 파일은 검사에서 발견돼요.

각 채점표에는 must_include, must_not, evaluation_scope, unknown_handling을 구분해요. 결과 기록용 양식은 생성된 `result-template.json`이에요. `execution-status.json`에는 실제 실행의 근거가 있는 경우에만 기록해요. 검사는 기록의 구조·입력 일치만 확인할 수 있고 그 기록이 진실임을 독립적으로 인증하지는 않아요. 실제 응답·사용자 자료가 있는 실행 기록은 공개 패키징에서 차단해요.

32개는 개발용 문제이며 DRAFT 7개, WASH 10개, REVIEW 15개예요. 규칙 28개 모두에 직접 연결을 만들었지만 이것은 행동 성능이나 충분한 시험 범위를 입증하지 않아요. 원문을 읽고 작성한 수동 예시는 별도 표시하며 외부 모델 시험으로 계산하지 않아요.
